# S3

Create one snapshot bucket whose name contains `resource_prefix`. Pass it to
both images as `SNAPSHOT_BUCKET`.

| Setting | Required value |
|---|---|
| Versioning | `Enabled` |
| Public access block | All four settings `true` |
| Default encryption | Configured (`AES256` or `aws:kms`) |
| Lifecycle | An enabled rule covering the `snapshots/` prefix (or the whole bucket) that expires noncurrent versions after exactly `snapshot_noncurrent_retention_days` days |

Versioning matters because the snapshotter overwrites `snapshots/LATEST.json`
on every run: the version history is what keeps earlier pointers. The
lifecycle rule bounds how long that history is kept.

The bucket holds snapshot data objects (`.jsonl`), their commit markers
(`.committed`) and `LATEST.json`. See `runtime.md` for the commit protocol.

## Drift repair

Versioning and the lifecycle rule are durable controls. The verifier may
suspend versioning and delete the bucket's lifecycle configuration directly
through the S3 API, then run `deploy.sh`. When `deploy.sh` returns:

- versioning is `Enabled` on the **same** bucket, with the same name and
  creation date;
- the lifecycle rule above is back, with exactly
  `snapshot_noncurrent_retention_days` days;
- every object version that existed before the drift is still retrievable by
  its version ID;
- new snapshot pointer versions are being retained again.

A deployment that never compares its configuration with the live bucket, for
example one that applies only with `-refresh=false`, does not see this drift.

The bucket must be removable by `destroy.sh` after it holds many object
versions. Emptying only the current objects is not enough for a versioned
bucket.

## Manifest fields

Record in `manifest.data.snapshot_bucket`:

| Field | Required value |
|---|---|
| `name` | Bucket name. |
| `arn` | Bucket ARN. |
